## Context

This is the first repository in the Greg AI Labs ecosystem. Its primary purpose is to be a
production-grade AI productivity platform and simultaneously serve as the canonical reference
implementation for educational content (eBook, bootcamp, video course).

The technology choices must:

1. Support modern full-stack development with strong TypeScript tooling.
2. Be beginner-accessible while being production-ready.
3. Minimize infrastructure complexity for a solo developer.
4. Enable AI features (LLM chat, coaching, analysis).
5. Demonstrate professional software engineering patterns (DI, Repository, Interface-first).

---

## Decision

The system uses Next.js 16 (App Router) + TypeScript + Supabase (PostgreSQL + Auth) +
OpenAI API, organized with a Layered Architecture using Repository Pattern and Dependency
Injection, developed with Claude Code as the primary engineering assistant.

---

## Rationale

### Framework: Next.js 16 (App Router)

| Option | Pros | Cons |
|---|---|---|
| Next.js 16 (chosen) | Full-stack in one repo, App Router, server components, built-in API routes, Vercel-ready | Breaking changes vs older Next.js training data; newer than most tutorials |
| Next.js 14 / 15 | More training data available | Already going stale; not the current release |
| Remix | Clean data patterns, progressive enhancement | Smaller ecosystem, less beginner recognition |
| Express + React SPA | Maximum control | Two repos, more infrastructure, slower to build |

**Deciding factors:** Single repo simplicity, App Router enables co-location of UI and API,
Vercel deployment is trivial, TypeScript support is first-class.

---

### Language: TypeScript (strict mode)

| Option | Pros | Cons |
|---|---|---|
| TypeScript strict (chosen) | Catches errors at compile time, excellent IDE support, required for production quality | Slower initial development for beginners |
| TypeScript lenient | Easier onboarding | Defeats the purpose of TypeScript |
| JavaScript | Fastest to prototype | No type safety, not suitable for a reference implementation |

**Deciding factor:** This codebase will be taught to developers. Strict TypeScript is non-negotiable
for any serious production application.

---

### Database & Auth: Supabase (PostgreSQL)

| Option | Pros | Cons |
|---|---|---|
| Supabase (chosen) | Managed PostgreSQL, built-in Auth, free tier, dashboard, storage, row-level security | Vendor dependency; service availability risk |
| PlanetScale | Serverless MySQL, branching | MySQL, not PostgreSQL; branching adds complexity |
| Neon | Serverless PostgreSQL, branching | Less batteries-included (no built-in auth) |
| Self-hosted PostgreSQL | Full control | Infrastructure overhead for a solo developer |
| Firebase | Easy auth and Firestore | Document database, not relational; limits query power |

**Deciding factors:** PostgreSQL is the right database for relational data with complex queries.
Supabase provides Auth, Storage, and a dashboard out of the box, eliminating three separate services.
The free tier is sufficient for development and early production use.

---

### AI Provider: OpenAI API

| Option | Pros | Cons |
|---|---|---|
| OpenAI API (chosen) | Best model quality, large ecosystem, well-documented | Cost per token; requires API key |
| Anthropic API (Claude) | Excellent for reasoning tasks | Less beginner documentation; no GPT-equivalent name recognition in courses |
| Google Gemini | Competitive pricing | Less established SDK patterns |
| Local models (Ollama) | No cost, offline | Hardware requirements; lower quality for production |

**Deciding factor:** OpenAI is the most recognizable AI provider for educational content. The
Provider abstraction layer means the underlying model can be swapped without changing business logic.

---

### Architecture Pattern: Repository + Dependency Injection

| Option | Pros | Cons |
|---|---|---|
| Repository + DI (chosen) | Testable, swappable data sources, clear separation of concerns | More files, steeper initial setup |
| Direct Supabase calls in API routes | Fast to write | Untestable, violates SRP, couples business logic to vendor |
| ORM (Prisma) | Auto-generated types, migrations tool | Additional abstraction layer; schema definition duplication |
| tRPC | Type-safe API layer | Requires specific client setup; less standard for learning |

**Deciding factors:** The Repository Pattern makes every Service unit-testable by injecting mock
repositories. This is the professional standard and critical for the educational mission of this project.

---

### AI-Assisted Development: Claude Code

| Option | Pros | Cons |
|---|---|---|
| Claude Code (chosen) | Handles boilerplate, enforces patterns, documents as it goes | Requires clear directives; no persistent session memory |
| GitHub Copilot | IDE integration | Autocompletion only; no agentic task execution |
| Manual coding | Full control | Slower; more opportunity for pattern drift |

**Deciding factor:** Claude Code can implement complete feature modules from specifications while
enforcing the architectural patterns defined in directives. This dramatically accelerates development
while maintaining professional standards.

---

## Consequences

### Positive

- Clean, testable architecture from day one.
- Supabase reduces infrastructure management to near zero.
- TypeScript strict mode catches bugs before runtime.
- Repository pattern makes swapping Supabase for another database feasible in the future.
- OpenAI provider abstraction means Claude API could be used instead with a single provider file change.
- Claude Code can maintain consistent patterns across the entire codebase session-to-session.

### Negative / Trade-offs

- More files per feature module than a simpler approach (DTOs, interfaces, services, repositories all separate).
- Supabase vendor dependency — if Supabase changes pricing or availability, migration is required.
- Next.js 16 (with React 19) is bleeding-edge — some libraries may not be compatible yet.
- Claude Code sessions lose context on restart — the documentation system must compensate.

### Neutral

- Docker is included for local parity and future Kubernetes deployment but not required for development.
- GitHub Actions CI runs on every push — ensures baseline quality but adds ~3 minutes to each push.
